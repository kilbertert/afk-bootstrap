# 11. 替身比真上游宽松：把「绿的测试不算证据」变成可执行的判据

日期：2026-10-18
状态：Accepted
影响版本：`scaffold/.sandcastle/review-prompt.md`、`scaffold/.sandcastle/review/prompt.md`、
`scaffold/.sandcastle/review/axis-prompt.md`（升级步骤 1.7.27 下发）；`TEMPLATE_VERSION` 1.7.26 → 1.7.27

## 背景

1.7.24 与 1.7.25 把对抗授权给了两条审查链路，并都写进了同一句话：
**「绿的测试不算证据」**。那句话说了**结论**，没给**理由**，也没给**动作**。
一个被要求「别信绿灯」的审查者，实际能做的只有「再多看几眼」。

让这句话可执行的东西在本仓之外被量出来了。AI-Ops 上线当天连续暴露三个缺陷，
**每一个的单测都是绿的**（该仓 ADR 0030）：

| # | 缺陷 | 单测为什么绿 |
|---|---|---|
| 1 | 请求发 `Accept: image/jpeg`，而真网关对那个端点**按 Accept 过滤**（非 `*/*` 一律 404） | 替身不看 Accept，一律回 200 |
| 2 | 参数放在 body，而真网关的两个过滤器**都只读 query string** | 替身只按 body 解析 |
| 3 | 只读 `results`，而真上游回的键是 `invitation_results` | 替身回的**就是** `results` |

三处形状相同：**替身实现的是「我以为上游会接受什么」，不是「上游真的接受什么」。**
它验证的是我们请求的**自洽性**，不是它的**可接受性** —— 前者必然通过，后者才是要被验证的。

关键性质：**放宽替身会提高覆盖率、降低保真度。** 所以「多写测试」不是解药，
覆盖率门槛也不是 —— 这三个缺陷发生在**已经写了 54 个用例**的模块里。
这决定了它只能是**审查判据**，不能是覆盖率目标。

## 决策

把 §4 写成两条可执行的判据，分别给两类审查者。

**只读审查者（`review/axis-prompt.md`）—— 给「怎么发现」。**
三步、可产出、不是感受：

1. 挑出本次改动里新增或改动的替身，以及它替代的那个真实系统。
2. 说出**一件真实系统会做而替身不做**的事 —— 它**拒绝**、忽略、要求、或以不同方式回答的。
   证据可以是对方客户端源码、API 文档、或抓到的真实响应；**要说明是哪一种**。
3. 说出「按真实行为，这段代码会怎样」。若与测试断言不同 —— 那就是发现：
   测试是绿的，因为替身宽松，不是因为代码对。

并点名**偏好令人不快的那些行为**：按请求头过滤的端点、只从 query string 读的参数、
真名与显然名字不同的字段、调用方没有的权限。**替身忠实于 happy path、对拒绝行为只字不提**，
是这个类别最常见的形态，而缺陷就住在拒绝里。

**可写审查者（`review-prompt.md`）—— 给「可跑的判据」。**
因为它能改，所以这一步能真的跑出来：

1. 说出真实系统的一件拒绝行为（同上，带出处）。
2. **把它加进替身。**
3. **跑测试。绿转红 = 抓到了这一类缺陷。** 改代码（不是把替身改回去），
   并让替身保持严格，在替身处留注释记下它复现了什么、出处是什么。
4. 什么都没转红，也**保留更严格的那个替身** —— 它不花什么，而且它才是真的 —— 并说明试过什么。

注释格式（沿用 AI-Ops 已验证的形状）：

```
⚠️ <真实系统> <做了 X>；替身必须复现，否则 <那个错误实现> 会一直绿着，直到撞上真的。
   出处：<YYYY-MM-DD 实测 / 哪份文档 / 哪个抓包>
```

**修复者（`review/prompt.md`）—— 给「别修错方向」。**
一条：当轴报告说某个假上游比真实系统宽松时，**修法绝不是放宽断言**，
而是让替身复现真实行为、让代码去适应。并留下出处注释 ——
**没有出处的严格替身，会被下一个读者当噪音删掉**。

三处都写了「本次改动没有替身就说明没有，继续走」：这是对「跟进程外的东西打交道」
的改动要问的问题，不是要凑的配额。

## 被否掉的替代形态

- **把 §4 做成覆盖率门槛或检查项。** 最省事，也最符合「把它自动化」的直觉。
  它输在**方向相反**：放宽替身会**提高**覆盖率，所以覆盖率门槛会奖励这个缺陷，
  而不是抓住它。这三个缺陷在 54 个绿用例里活了很久，正是因为这个。
  能抓住它的只有「读替身、问它哪里比现实宽松」——那是判断，不是计数。

- **只写进只读审查者（`review/axis-prompt.md`）。** 只读那条能**发现**，
  但不能**验证** —— 它被禁止改文件，所以无法「把行为加进替身、看测试转红」。
  而「绿转红」恰恰是这个判据唯一的客观信号。把可跑的那一半给能改的人，
  是让这条判据不依赖审查者的自信。

- **用锚点编辑（1.7.23 对 `implement*` 的做法）而不是 `cmp` 整替。**
  1.7.23 之所以用锚点，是因为那些文件在每个消费仓里差 9–25 行手写段落。
  **本轮实测：这三个文件不一样。** 归一化掉语言替换之后，
  三个消费仓与 scaffold **都是 0 行差异**。所以 `cmp` 在这里是对的，
  而锚点会为了改一整节去拼三个不同的锚点。同 1.7.25 那条规矩：
  **`cmp` 适合没人改过的文件，锚点适合人人都改过的 —— 而「人人都改过」必须逐文件量，不能猜。**

- **整替之后不管语言替换。** 整替会把 scaffold 的 `npm run check` 写回
  Python 仓已经翻译过的文件里 —— 那正是 1.7.26 刚修掉的缺陷，一步之后又被引回来。
  所以整替之后必须重跑 `tools/adapt-check-command.mjs`。这一条是**靠算出来**的，
  不是靠跑出来：写的时候就发现「整替」与「1.7.26 的翻译」会打架。
  它也有负向对照钉住（去掉重跑 → smoke 报「reverted a python consumer's check command to npm」）。

## 后果

- 三个消费仓 dry-run 都只改这三个文件，且**没有一行 `npm run check` 残留**。
- **判错上游行为的代价继续前移**：从「部署那天」到「写替身那天」，
  现在再到「审查那天」。
- **代价（说清楚）**：这是一条**审查判据**，不是门禁 —— 它靠审查者执行，
  没有任何检查会因为忽略它而失败。本仓的惯例如此（见 `SERVER-DEVELOPMENT-CONSENSUS`
  的 Enforcement 段：没有检查的规则仍然有约束力，但操作者是唯一控制点）。
  不把它做成门禁是**故意的**：能自动判的只有「替身注释里有没有出处」这种形状，
  而那会奖励写注释、不奖励想清楚。
- **仍未做**：`TEST-DISCIPLINE.md` 的 §3.1（禁变更探针）与 §3.3（「已验证」不得引用测试绿灯）
  仍是纸面的。§3.1 实测下来探针类测试只占 3%，收益小、扰动大（会让 review 开始挑既有测试的措辞），
  **故意不下发**。§3.3 与本条同源，将来若下发，落点也在这三处。
