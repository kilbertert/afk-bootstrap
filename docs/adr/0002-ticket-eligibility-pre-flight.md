# 2. 授权之前先判「这张单能不能做完」

日期：2026-10-12
状态：已采纳
影响版本：afk-bootstrap 1.7.18（`upgrade-afk.sh` 的 `1.7.17 -> 1.7.18` 步骤）

## 背景

工作流一直有一道**形状门**：`agent-implement.yml` 拒绝 PRD、拒绝子单、拒绝还有未关闭
原生阻塞的单。这三条判的都是这张单在**图里的位置**。

从来没有任何东西判过这张单**本身**——它有没有说清要做什么、"做完"长什么样。于是
`agent:implement` 打开的那扇门，另一侧无人把关。本机实测（带正文的 open issue）：

| 仓库 | open | 有验收标准 | 有非目标 |
| --- | --- | --- | --- |
| Health-Flow | 0 | – | – |
| genesis-evidence | 5 | 3/5 | 3/5 |
| AI-Ops | 14 | 3/14 | 8/14 |
| Auto_Test | 27 | 11/27 | 11/27 |

而在 `ready-for-agent` 这个**授权标签**上：三个仓库十二张单，**只有一张**有验收标准。
门开着的，进去的单三成有。

真正的触发来自 GitHub 之外。本机禅道实例里的需求单**只有一个标题**——实测一个产品
20/20、一个项目 14/14 的 `spec` 与 `verify` 同时为空。像
`视频详情页面主图需要调整大小===泉哥（需出原型给开发，如抖音）` 这样的单**开不了工**：
没有可观察的结果可做，agent 拿到它只会**自己编一个**，而编造就是代价。

所以需求平台要的第一件东西不是连接器，是对**这张单**的判断。

## 决定

**新增 `.sandcastle/ticket-check.mjs`，并在两条授权入口做 pre-flight。**

判据本身（机器可判的部分）：

| | 规则 | 拦的是什么 |
| --- | --- | --- |
| **失败** | 有标题也有正文 | 标题不是规格 |
| **失败** | 验收标准 | 没说"做完的样子"，agent 只能编 |
| **失败** | 一个有形的东西（文件、符号、命令、代码跨度） | 看不出改动落在哪，只能猜 |
| **失败** | 没有未决的二选一 | "首选 A / 次选 B"意味着**选本身就是决策** |
| 警告 | 非目标一节 | 改动没有边界 |
| 警告 | 问题陈述 | 缘由没写下来 |

验收标准用标题（`## Acceptance criteria` / `验收` / `完成标准` / `期望行为` /
`Done when` **以及 `planner.ts` 现有的四个英文标题**）、行内标签、或**一串可核对的步骤**
都算——取证单没有标题、也不改文件，它照样是 agent 能做完的单。

**PRD 放行，不拦**。它是容器，工作流本来就拒绝直接实现它；用 `planner.ts` 同一套判据
（`Problem Statement` + `Solution` + `User Stories` 三个标题，或标题含 `PRD`/`[spec]`）
认出它并豁免，它的子单各自过门。

**豁免是断言，不是沉默**：契约在别处就在单里写一行 `No-acceptance: <理由>`。这一行**会被
读**，因为"有意不写"和"忘了写"在一张单里长得一模一样。豁免**不覆盖未决的二选一**——
它说的是契约在哪，说不了两个方案里做哪个。

三种模式沿用本机已有的 `adr.check.mjs` 形态：`--title/--body`（报告，退出 0；`--strict`
才当门）、`--json`（读 `gh issue view` 的原样输出）、`--manifest`（读一份列表，含
`{data:[...]}`，报"N/M 条可实现"，`--min-pass` 才决定退出码）。**不需要连到那个平台**
就能回答"这批单能不能交给 agent"。

## 理由

1. **判结构，不判判断。** 四条硬规则问的是同一件事的四种写法："这段文字在不在、空不空、
   有没有点名可核对的东西"——都不需要理解改动内容。判据**判不了**的部分（验收标准对不对、
   点名的文件是不是真要改、这活值不值得做）写在文件头里说清楚，不假装。
2. **门槛压低，因为高门槛会被关掉。** 两条只警告的规则是真信号，但没有它们的单是**更差的
   单**，不是**做不了的单**。在品味上失败的检查会被停用。
3. **门与报告分开，和 `adr.check.mjs` 同形。** 读一张单不该让 shell 失败；要门的调用方
   显式说 `--strict`。而**要门却给了空输入**是配置错误，照样硬失败。
4. **两条入口都接。** 单 issue 走 `agent-implement.yml` 的 pre-flight；PRD 的子单循环在
   **开工前过同一道闸**，不通过就**跳过该叶子单并留评论**，不否掉整个 PRD——一张写糊的
   子单不该挡住它后面的每一个兄弟。

## 被否掉的方案

- **加一个门，不做判据（只拒绝"没有正文"）。** 最省事，但拦不住本机绝大多数不合格的单：
  Auto-Test 那 11 张无验收标准的单**都有正文**。
- **整棵树/整批硬门（`--min-pass` 默认卡死）。** 会把 14/14 全不合格的禅道项目直接判死，
  操作员无法开工。比率是策略数字，不是事实，所以默认只报告。
- **让判据也判"验收标准写得对不对"。** 只能靠猜，结果要么全放过要么全拦死。
- **把禅道/Slack 直连 AFK 沙箱，让 agent 直接读源单。** 沙箱跑的是候选代码，给它开一个
  通到生产系统的窗口是授权不是便利；而且**直连把问题搬了个位置**——agent 读到同一段没
  规格的文字，还少了"有人被迫说清做完的样子"这一步。先翻译成 GitHub 单，再授权。
- **Dify / 外部编排器做门。** 本机 2026-10 在 AI-Ops 上试过（#577），结论是迁移面太大、
  且把运行时与租户交给外部。判据放仓库里，跟着 commit 走。

## 后果

- **每个项目都会多一个 pre-flight 步骤。** 已授权的单过不了会被拒绝、摘标签、写评论——
  这是**行为变化**，需要操作员知道。
- **一条本机建立的惯例被写进模板**：`docs/agents/ticket-contract.md` 是**新文件**，不是
  往 `issue-tracker.md` 里加一节——实测四个仓库都已经有自己的 `issue-tracker.md`
  （副本早于本模板），只在"文件不存在时"写入的步骤**一个仓库都到不了**。
- `ticket-check.mjs` 与 `docs/agents/ticket-contract.md` 都是新的，代码与文档**同时**进入，
  两者会漂移的风险由 `--self-check` 挡住一半（它有负向对照，注入 bug 必须变红）。
- 判据的**误伤面**：写得好的调查报告（AI-Ops #619/#617）会因"未决二选一"或"缺验收标准"
  失败。这是**有意的**——它确实不是 agent 能做完的单，但它仍然是有用的文档。规则对
  `首选/次选` 这种作者自己的措辞收窄到必须成对出现，单独的"首选"不算分叉。

## 验证

`test/smoke.sh` 新增一段（node 与 python 各跑一次，都通过），断言：

- 迁移后 `ticket-check.mjs`、`docs/agents/ticket-contract.md` 到位；
- 两个 prompt 都出现 `Source ticket:`；
- **插入的段落与脚手架逐字节相同**（新 bootstrap 的项目与升级来的项目必须对同一条规则
  说同样的话）；
- 发布的 checker 在**它被发布的地方**跑通 `--self-check`；
- 单 issue 工作流的 pre-flight **在解析结果上**成立（步骤存在、顺序在 open-PR 之前、
  open-PR 被它 gate）；**负向对照**：把这一步剥掉，同一个判据必须不再成立。

## 顺手修掉的一个既有缺陷

铺之前先拿四个消费仓库逐个数了一遍，发现**每个仓库都恰好有 3 份**
`*-adr-check-scope-and-self-application.md`——1.7.13 引入的那个步骤把记录文件名写成
"下一个空号"，而这个号**每次运行都重算**，于是"已经存在"这个判据永远命中不了：
每次升级经过那一步就再写一份。四个仓库各 3 份，各自对应 1.7.13 之后的每次升级。

改成锚在**slug**上（文件名的词干，不含号），并在这轮实测：3 份的仓库不再多出第 4 份；
0 份的仓库仍会写 1 份（负向对照，否则前一条只证明了"这个步骤什么都不做"）。

多出来的副本**只报告、不删除**：内容完全相同，且按文件名被 commit 与约定文档引用，
删哪几份是项目自己的决定。

## 一件有意没做的事

`planner.ts`（`pnpm ralph`）**一行没改**。`agent:implement` 这条主路径由 label 触发、
走 GitHub Actions，`planner.ts` 不参与；给它加判据会覆盖不到真实入口，反而制造"两个地方
各有一套判据"的分叉。要动它时，判据应当复用同一个 `ticket-check.mjs`，不是重写一遍。
